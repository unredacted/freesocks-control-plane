# Client compatibility CI

`bun run test:compat` boots a disposable Remnawave backend, issues a test user, renders subscriptions through FCP's actual HTTP handler, and runs pinned client engines and the SFL Linux package. No existing account or production credentials are needed. Everything is in the **Client compatibility** workflow; the existing fast suite remains offline.

## What is proved

| Check                | Environment                                                                                | Acceptance                                                                                                                                                                                                                                                |
| -------------------- | ------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Catalog coverage     | Offline                                                                                    | Every enabled default recommendation has a coverage entry; missing entries fail CI.                                                                                                                                                                       |
| Subscription formats | Real Remnawave + FCP handlers in `convex-test`                                             | Nonempty expected format for each User-Agent; a weak validator on every answer and a 304 when it is sent back; cache isolation; changed Host observed after cache invalidation; invalid subscription rejected.                                            |

| Shipped templates    | Real Remnawave serving FCP's own templates, the same pinned engines                        | sing-box and Mihomo run the served body with only listener, DNS and controller changed, routing asserted unchanged; reaching the isolated origin proves the default route takes the proxy. The legacy Clash body's default route is checked statically.   |
| Network controls     | Separate Docker networks                                                                   | Origin unreachable directly; wrong VLESS credential cannot pass through a fallback.                                                                                                                                                                       |
| Packaged SFL         | Installed checksum-verified `.deb`, Debian container + Xvfb + the app's own daemon         | Actual application opens generated deep link, accepts manually entered URL, validates and saves config with bundled core, then updates remote profile. Its real HTTP User-Agent is asserted.                                                              |

| Edge connection      | Real panel and relay nodes, fake edges, pinned sing-box and Mihomo (see "Edge connection") | Every cell of the supported matrix (docs/edges.md): a member connects through its L4 or L7 edge with each engine the cell claims, after FCP takes the node through the real lifecycle; the body names no origin and the member network reaches no node.   |
| Deployed smoke       | Actual public FCP fronts/mirrors                                                           | Dedicated canary subscription returns expected format, cache headers and native engine validation; its weak validator survives identity, gzip and zstd delivery and a revalidation is a 304. Read only; does not connect the tunnel.                      |

The integration harness executes FCP's real route, provider and cache logic in the **Convex test runtime**, not a deployed Convex server. The live backend and proxy traffic are real. The deployed smoke workflow covers the public HTTP deployment separately. Backend authentication and rate-limit behavior remain covered by the normal backend suite; the report-form browser tests inject 401/429/502 responses and do not perform a real login.

A reference engine pass is **not** a packaged Hiddify, Karing, Clash, or mobile application pass. Contract User-Agents are regression inputs, not assertions about every current app release. The exact SFL 1.14.0 identity was extracted from its checksum-verified package: `SFL (sing-box 1.14.0; language en_US)`. This exposed the old FCP normalization rule's missing space/parenthesis form. SFW uses the same form with a different prefix (upstream `sing-box-for-desktop/src/main/userAgent.ts` picks `SFL` on Linux and `SFW` otherwise); only the SFL string is captured from a package here.

The packaged app shows its main UI, and validates every imported profile (`checkConfig`), only through its bundled `sing-box-daemon`, which the `.deb` normally starts via systemd. Without it the app sits on a "Cannot connect to the sing-box service" screen and the import dialog never mounts. `docker/compat/sfl-entrypoint.sh` therefore starts the daemon exactly as the shipped unit file does (`run --working-directory /var/lib/sing-box-daemon --socket /run/sing-box.socket`), waits for the socket, then runs the driver under Xvfb; on the Xfce VM runners the package's own postinst starts the real service. The driver (`tests/compat/sfl.ts`) attaches to the Electron renderer over CDP (`--remote-debugging-port=0`) because the official build disables Node inspector arguments, and it selects the main window by URL because the app also owns a tray window.

The tunnel fixture uses a minimal, test-owned Remnawave template with a SOCKS listener and REALITY outbound, and a sing-box server. The shipped-template check then switches the panel to the templates FCP ships (byte for byte what backend setup and its re-sync install) and runs each served body as it is: only the listener, the DNS servers and the controller change (`tests/compat/sandbox.ts`), and the routing (proxies, groups, Mihomo `mode` and `rules`, the sing-box `route`) is asserted unchanged. The panel's legacy Clash output (any other `clash…` User-Agent, the CLASH template) leaves VLESS out, since legacy Clash has none, so that body has no entry to run and only its routing is checked. The client network cannot reach the origin, so the probe passes only when the body's own default route takes the proxy: a template that sends unmatched traffic direct fails it, as the Clash and Mihomo templates' `mode: global` would have (global mode ignores `rules:` and routes through Mihomo's built-in GLOBAL group, which is DIRECT). The same rule is pinned offline on every template and on rendered member bodies (`defaultRouteFaults`, `convex/lib/backend/subscriptionTemplates/defaultRoute.ts`). Engine readiness is two-stage: the SOCKS listener accepting TCP, then the HTTPS probe itself, which retries a bounded few times on transient curl exits (7, 28, 35, 56) because mihomo binds its listener before its tunnel reaches the running state and closes connections handed over in that window ("Send failure: Broken pipe"). Every attempt fails against a wrong credential, so the negative test still fails closed. It does not certify the production templates' individual rules beyond where unmatched traffic goes, Xray server compatibility, TUN integration, IPv6, QR decoding, browser/OS protocol registration, or platform-specific HWID behavior. The existing subscription-front tests cover HWID forwarding/cache isolation; physical client HWID behavior requires device evidence. Outline's existing provider tests remain the automated backend coverage; its application and transport are not exercised here.

## Running locally

Requirements: Docker Compose, Bun, Node 22/24, OpenSSL, and outbound access to the pinned GitHub releases and container registries. Linux x64 is the CI target; Docker Desktop with Rosetta emulation runs the amd64 engines and the Electron app on Apple Silicon (the packaged-SFL step takes about 40 seconds there; a full run about 4 minutes with warm images). Node 22/24 is recommended for Playwright; the local Node 26 browser downloader has exhibited a hang.

```sh
bun install --frozen-lockfile
bun run test:compat
bunx playwright install chromium firefox
bun run test:compat:browser
bun --no-env-file scripts/compat/report.ts
```

The integration stack binds loopback port 3000 and the packaged-app bridge uses port 4179. Do not run it concurrently with another Remnawave integration stack. Both backend fixtures and generated private keys are throwaway. The wrapper always tears down its own Compose project and volumes; it never uses the application's production Compose project. `.cache/compat` and `test-results` are ignored by Git. The application runs with a fresh user-data directory.

Downloads verify pinned SHA-256 before extraction/execution. `FCP_COMPAT_CHANNEL=latest` instead resolves official stable release assets and their GitHub SHA-256 digests, then executes the same tests; this runs nightly separately from the pinned PR gate. It does not rewrite the committed pins. A changed upstream import UI or format fails discovery and requires review before updating the pins.

The public artifact contains test names, statuses, artifact versions/hashes and coverage limitations. Raw JUnit failures, generated configurations and engine logs are not uploaded because they can contain credentials. Browser traces/screenshots contain only fixture data. Packaged app screenshots are retained locally under `test-results/compat/sfl` for debugging.

## Edge connection

`bun run test:integration:edge-connection` (job **Member connects through an edge**) is the release gate for edges and the proof behind the supported matrix (`docs/edges.md` "Supported matrix", `tests/compat/manifest.ts` `edgeMatrix`): a member connects THROUGH an edge with real software end to end, for every cell the matrix claims. The subscription checks above prove what FCP serves; this one proves that what it serves after a node is protected actually carries a member's traffic through the intended edge, and around nothing else.

| Piece          | What runs                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Panel          | The ephemeral Remnawave panel of `docker-compose.remnawave-test.yml`.                                                                                                                                                                                                                                                                                                                                                                                              |
| Enrolled nodes | Real `remnawave/node`s the node role's contract enrolls, serving FCP's own profile: `freedom-reality` and `freedom-xhttp` (XHTTP under REALITY) on their public port, fronted at L4; `freedom-ws` on loopback behind its ingress (Caddy in the node's network namespace, TLS for the origin hostname), at L7.                                                                                                                                                      |
| Operator nodes | Real `remnawave/node`s serving a profile the operator wrote (`tests/edge-connection/cells.ts`), managed by the panel at their public address and served direct first: eight transports at L4 (VLESS over TLS, WebSocket, HTTP Upgrade, gRPC and XHTTP; Trojan over TLS and WebSocket; Shadowsocks), four HTTP transports at L7 (HTTP Upgrade, gRPC on 443, XHTTP packet-up, Trojan over WebSocket). Xray terminates TLS itself with a per-run certificate.         |
| L4 edge        | A plain TCP forwarder (`docker/edge-connection-test/forwarder.ts`) answering on one address per load balancer. The fake UpCloud API hands out the next address of its pool and wires it to exactly the backend FCP asked for.                                                                                                                                                                                                                                      |
| L7 edge        | A CDN-style front (Caddy): TLS for the fake Cloudflare zone, and one route per proxied record, added through its admin endpoint by the fake API: the record's content on the zone's port 443 or its Origin Rule's, the origin certificate verified, the front's hostname passed as the Host. As Cloudflare does, it sends the member's address in `X-Forwarded-For` always and in `CF-Connecting-IP` unless the record's request-header Transform Rule removes it. |
| Member         | The pinned sing-box and Mihomo of the compat suite, on a network that reaches only the edges.                                                                                                                                                                                                                                                                                                                                                                      |
| Page           | A web page on a network only the nodes join, answering a per-run token.                                                                                                                                                                                                                                                                                                                                                                                            |
| FCP            | `convex-test` in a runner container on the nodes' network, so its own checks (the ingress check, the origin probe, the front proof) reach the nodes the way production does.                                                                                                                                                                                                                                                                                       |

What the tests assert (`tests/edge-connection/`):

- **Wiring** (`wiring.integration.test.ts`, no FCP): with hand-written configs, a REALITY session through the forwarder and a WebSocket session through the front each fetch the page, and so does every operator transport through its own edge with every engine that speaks it; the member network reaches no node and no page directly, and the node's ingress sees the front, never the member. A failure here is the topology's, not FCP's.
- **Member** (`member.integration.test.ts`): for each enrolled node, enrollment and the role's applied report reach `machine_ready` (for the WebSocket node through FCP's own ingress check against the real ingress); a member issued into the node's mode gets nothing that names the origin while the node is not live; the guided setup run provisions through the real adapter, for L4 builds the real Try it link, which the engine that speaks it imports and connects through the candidate edge BEFORE the tick, for L7 runs the real front proof through the front and the node; the run parks at publish until the node is approved over the admin HTTP routes, then hides, rehearses over the panel's real bodies and goes live. For each operator node, the guided setup run discovers every transport, fronts each with its own edge (every L4 link tried before the tick, every L7 front proved, VLESS or Trojan), hides the direct Hosts and finishes without an approval (FCP does not manage the node). Then, per tested cell and per engine the cell claims, the member whose key lands on that cell's edge (a member gets a primary and a backup edge of the node's pool; the test re-keys until it is this one) fetches `/api/v1/sub/<token>` with the engine's User-Agent: every endpoint is one of the node's edges on 443, no node address or origin hostname appears, and the engine fetches the page through the cell's entry, counted by the forwarder at that edge's address or logged by the front for that hostname from the member's address. Through the WebSocket node's front, the node's ingress also logs what the front sent it: no `CF-Connecting-IP` (FCP's header rule for the front's name removed it) and the member's address in `X-Forwarded-For`, which no rule removes at Cloudflare and the node itself must drop (docs/edges.md "Cloudflare fronts"). Last, FCP reached nothing but the panel and the fake providers. Every tested cell of the manifest must have a case (`cells.ts` refuses a claim without one).

Seams: the outside probe round that verifies an L4 standby (its evidence lands as Globalping's would), and two stand-ins inside the otherwise real L7 front proof (the front is dialled at its address instead of through public DNS; its neutral 204 is the stack's page). The provider APIs are fakes behind the real adapters. A served body is adapted to the sandbox before it runs, and only that (the test asserts the rendered proxies are untouched, `tests/edge-connection/clients.ts`): the TUN inbound is dropped (the container has no TUN device; a local listener carries the requests), the DNS servers point at the client network's resolver (it has no public one), a Mihomo body loses its controller and extra ports, and the test picks which of the body's proxies carries its request (sing-box `route.final`, a Mihomo `MATCH` rule). A Mihomo body keeps its own `mode` (in any other mode Mihomo ignores the picked rule), and before any of it the served body's own default route must take its proxies (`defaultRouteFaults`). An operator node's qualification and test-link credential is minted on the default mode's group, so the test makes that node's mode the default while its run goes (the operator's choice of mode for a node FCP does not manage).

Facts the stack pins down: Xray refuses sing-box and Mihomo over REALITY unless the transport sets `minClientVer` low enough (FCP's profile template sets `1.8.1`, which is what lets sing-box in; § "REALITY client versions"), and refuses to proxy to private or reserved addresses, RFC 5737 included, so the page's network uses a public-looking range that routes nowhere. A gRPC origin offers `h2` alone, so FCP's origin probe offers it too (an `http/1.1`-only handshake is refused and the transport would never be offered an L7 account). Mihomo's XHTTP needs HTTP/2 to the front: an XHTTP transport whose TLS offers only `http/1.1` reaches the front with nothing it will speak. The panel hands a node only the users that exist when it starts it, or that it adds once the node is up: a user created while a node is still starting can miss it, so the wiring test creates its user before its nodes (members of the lifecycle test are issued long after their node is up).

Locally it needs Docker (amd64 sing-box runs under emulation on Apple Silicon) and takes about two minutes once images and the runner's dependencies are cached (the first run pulls the images and installs dependencies into a Docker volume). It binds the panel's loopback port 3000 like the other Remnawave stacks, so never run it alongside them. The script always tears its project down; `EC_KEEP=1` leaves the stack up for debugging, and the next run starts with a teardown. Nothing it keeps outside `.cache/edge-connection-test` (wiped each run) and nothing it prints carries a credential: node logs, client configs and subscription bodies are never echoed, and CI uploads no artifact.

## REALITY client versions

Every REALITY client puts a version in its Client Hello, and the server lets it in only between the transport's `minClientVer` and `maxClientVer` (both inclusive). What each family sends:

| Client family                                                | Version it sends     |
| ------------------------------------------------------------ | -------------------- |
| Xray-based (v2rayN, v2rayNG, Happ)                           | its own Xray version |
| sing-box and the apps on it (SFA, SFI, SFM, Hiddify, Karing) | 1.8.1                |
| Mihomo and the apps on it (Clash Verge, FlClash)             | 1.8.2                |

A transport that sets no `minClientVer` has no minimum, except on Xray-core v26.7.11 to v26.7.28 (commit af7eb680), which take 26.3.27: there a hand-built transport admits recent Xray clients only, and every sing-box or Mihomo member fails with `reality verification failed` while a test made with an Xray client passes. `"minClientVer": "1.8.1"` admits every family on those releases. Commit 47cfe999 took the default out again (v26.9.8, a build later withdrawn as a release, and v26.9.9), and brought XTLS/REALITY 8cdf7bf9 with it: from then on the server refuses a Client Hello that does not offer X25519MLKEM768 ahead of X25519. sing-box strips that key share from its REALITY Client Hello (SagerNet/sing-box issue 4520, open as of sing-box 1.14.1), so no transport setting lets a sing-box client in on v26.9.8 or later; the reports there have Mihomo 1.19.30 connecting, while an older Mihomo may need `support-x25519mlkem768` in its configuration. FCP judges a transport it did not build before members move onto it (the protect plan, the test card, the adopt dialog) and keeps judging a protected one (attention `reality_refuses_clients`), each restriction named with its own fix; docs/edges.md § "Protecting a node FCP does not manage" has the details. After a node upgrade, test each family, not only an Xray client.

## Full desktop VMs

The Debian container smoke test is not an Xfce test. The same SFL adapter can run on disposable, signed-in Xfce VMs with labels `fcp-debian-13-xfce` and `fcp-mx-25-2-xfce`. Provision Docker, Node 24, Bun and a running Xfce desktop session; run the Actions runner inside that session so DISPLAY, XAUTHORITY and DBUS_SESSION_BUS_ADDRESS are available. Allow package installation for that disposable runner. Record and pin the OS image/checksum in the VM provisioning system.

The nightly schedule also runs the provider contract test against a Remnawave 2.x backend (`REMNAWAVE_TEST_IMAGE=remnawave/backend:2.8.0`): production runs 3.x, but the provider stays dual-contract for backends that have not upgraded, and nothing on the PR gate boots a 2.x backend.

Enable repository variable `CLIENT_COMPAT_VM_RUNNERS=true` only after those runners are available. The job installs the verified package and sets `FCP_COMPAT_SFL_EXECUTABLE` to drive the actual desktop application. These jobs only run trusted main-branch code, never pull-request code. Destroy or reset each VM after the job. The runner label identifies the intended OS; inspect the OS record in the application result when certifying it.

## Deployed canaries

Create a dedicated test subscription and configure the `client-compatibility` Actions environment secret `FCP_COMPAT_SMOKE_TARGETS`:

```json
[
  { "name": "primary", "url": "https://example.test/api/v1/sub/DEDICATED_CANARY" },
  { "name": "mirror", "url": "https://mirror.example.test/api/v1/sub/DEDICATED_CANARY" }
]
```

Run **Deployed client compatibility** after deploying or changing a CDN/mirror configuration. Missing targets fail explicitly. HTTP redirects, errors, empty/wrong formats, unsafe shared-cache responses and invalid native configs fail. Once per target, the `revalidate` stage fetches the canary as identity, gzip and zstd: each answer must carry the same weak `W/"fs1-…"` validator (a proxy that rewrites or suffixes it fails), a compressed answer must vary on `Accept-Encoding`, and sending the validator back must return 304 (once per target because the per-token throttle would not carry it for every client). This workflow never creates, rotates or deletes an account. Use an unrestricted test tier for the format matrix; device-limit testing is a separate capability check.

No client honours `Retry-After`. What follows from the table:

- **The hint reaches four apps.** Hiddify and Mihomo Party re-read `profile-update-interval` on every update, Clash Verge Rev only at import, Throne only when the member opts in. Hiddify rejects a fractional value, which is why FCP sends whole hours. Everyone else refreshes on their own schedule (the sing-box apps every 60 minutes by default) or only by hand, which is what the backup entry and the drains are for (`docs/edges.md` "How fast members move").
- **Revalidation is the FreeSocks app's and the Mihomo core's.** No app sends `If-None-Match` for its subscription; the Mihomo core does for a proxy-provider. The 304 path is built for an app that polls often.
- **Never a 200 for a refusal.** v2rayN removes a subscription's servers before parsing the new body, so a 2xx carrying an error page would wipe them; every other client keeps its configuration on a non-2xx. FCP answers a refusal with 503 (edge-required) or 502 (backend down), never an empty or error 200.
- **Outline caches nothing.** A dynamic key follows a rotation on the next connect, and a 503 means that connect fails until the key renders again.

## Application certification and adding coverage

`tests/compat/manifest.ts` records each catalog client's scope and remaining gaps. Add an entry whenever adding a default recommendation. For CMS-only recommendations, review/export the live catalog before a release: the offline coverage guard cannot inspect a production database. Add an adapter for the actual package instead of relabeling a shared engine test as application coverage.

Apps needing Apple hardware, Android devices, licensed installs or missing automation are explicitly unverified. `scripts/compat/certify.ts` fails until every recommended app has recent application evidence for the exact requested FCP commit in `tests/compat/application-evidence.json`. The committed file starts empty intentionally. Set `FCP_COMPAT_CERTIFY_COMMIT` and run the command as a release checklist gate; never invent passes to make it green. Each entry records:

- client, exact app version, OS, backend version and 40-character FCP commit;
- UTC `testedAt`, tester, and a URL to the test evidence;
- `import`, `connection`, `dns`, `https`: `passed`;
- `refresh`: `passed` (or `not-applicable` for Outline's static key).

Evidence expires after 30 days and certifies only the recorded configuration/version/OS. This is the place to attach full TUN/device tests; the automatic engine and SFL import jobs alone cannot certify every client. Configure branch protection to require **Subscriptions, engines and packaged SFL** and **Report form (Chromium and Firefox)**. A green PR means those automated checks passed; full application certification remains a distinct release decision.
