# Client compatibility CI

`bun run test:compat` boots a disposable Remnawave backend, issues a test user, renders subscriptions through FCP's actual HTTP handler, and runs pinned client engines and the SFL Linux package. No existing account or production credentials are needed. Everything is in the **Client compatibility** workflow; the existing fast suite remains offline.

The panel fixture has three VLESS/REALITY Hosts of one node, with distinct ports and server names. Every catalogued subscription User-Agent must receive all three exact endpoint identities, with unique names; sing-box and Clash/Mihomo must expose every entry through the default selector. The checks run on the initial response, a cache hit, and after an upstream Host address changes and the cache is invalidated. A valid configuration reduced to one entry fails, as does a three-entry configuration whose selector includes only one. The offline regression suite checks those failures through pinning and member-facing renaming too.

Clash Verge, FlClash, Clash Meta for Android and Clash Party each run their own served bodies in the pinned Mihomo engine with FCP's shipped templates. FlClash includes the default User-Agent forms defined by [v0.9.2's package helper](https://github.com/chen08209/FlClash/blob/v0.9.2/lib/common/package.dart), including the `clash-verge` token and Linux, Android, Windows and macOS platform suffixes, alongside the older regression input. The shipped-template tests first connect with the served default routing unchanged, then narrow the selector to each proxy in turn and fetch HTTPS through it. The same checks run for every sing-box-format User-Agent, including Karing. A working first proxy cannot hide a broken second or third proxy. Both engines also reject the connection when every VLESS credential is wrong. These are subscription and reference-engine checks; packaged FlClash and other client GUIs still need application evidence.

The integration harness executes FCP's real route, provider and cache logic in the **Convex test runtime**, not a deployed Convex server. The live backend and proxy traffic are real. The deployed smoke workflow covers the public HTTP deployment separately. Backend authentication and rate-limit behavior remain covered by the normal backend suite; the report-form browser tests inject 401/429/502 responses and do not perform a real login.

A reference engine pass is **not** a packaged Hiddify, Karing, Clash, or mobile application pass. Contract User-Agents are regression inputs; each catalog app's list includes at least one string it really sends (§ "App User-Agents"), but no single string stands for every release. The exact SFL 1.14.0 identity was extracted from its checksum-verified package: `SFL (sing-box 1.14.0; language en_US)`. This exposed the old FCP normalization rule's missing space/parenthesis form. SFW uses the same form with a different prefix (upstream `sing-box-for-desktop/src/main/userAgent.ts` picks `SFL` on Linux and `SFW` otherwise); only the SFL string is captured from a package here.

The packaged app shows its main UI, and validates every imported profile (`checkConfig`), only through its bundled `sing-box-daemon`, which the `.deb` normally starts via systemd. Without it the app sits on a "Cannot connect to the sing-box service" screen and the import dialog never mounts. `docker/compat/sfl-entrypoint.sh` therefore starts the daemon exactly as the shipped unit file does (`run --working-directory /var/lib/sing-box-daemon --socket /run/sing-box.socket`), waits for the socket, then runs the driver under Xvfb as the unprivileged `fcp-browser` user. Only the daemon runs as root. The container uses `docker/compat/seccomp_profile.json`, adapted from [Playwright v1.64.1](https://github.com/microsoft/playwright/blob/v1.64.1/utils/docker/seccomp_profile.json) under its adjacent Apache-2.0 license: it retains the default-deny Docker policy while permitting `clone`, `setns` and `unshare` for Chromium's sandbox. It adds Docker's `clone3` ENOSYS rule so newer glibc versions can fall back to `clone`. No privileged container or added capabilities are needed. On the Xfce VM runners the package's own postinst starts the real service and the desktop user runs the driver. The driver (`tests/compat/sfl.ts`) explicitly enables Electron's sandbox and refuses root execution. It attaches to the renderer over CDP (`--remote-debugging-port=0`) because the official build disables Node inspector arguments, and selects the main window by URL because the app also owns a tray window.

The tunnel fixture uses a minimal, test-owned Remnawave template with a SOCKS listener and REALITY outbound, and a sing-box server. The shipped-template check then switches the panel to the templates FCP ships (byte for byte what backend setup and its re-sync install) and runs each served body as it is: only the listener, the DNS servers and the controller change (`tests/compat/sandbox.ts`), and the routing (proxies, groups, Mihomo `mode` and `rules`, the sing-box `route`) is asserted unchanged. The panel's legacy Clash output (any other `clash…` User-Agent, the CLASH template) leaves VLESS out, since legacy Clash has none, so FCP answers that app the app notice instead (§ "Apps too old to connect"): the suite checks it is one, that `mihomo -t` passes on it, and that the HTTPS probe fails through it. The client network cannot reach the origin, so the probe passes only when the body's own default route takes the proxy: a template that sends unmatched traffic direct fails it, as the Clash and Mihomo templates' `mode: global` would have (global mode ignores `rules:` and routes through Mihomo's built-in GLOBAL group, which is DIRECT). The same rule is pinned offline on every template and on rendered member bodies (`defaultRouteFaults`, `convex/lib/backend/subscriptionTemplates/defaultRoute.ts`). Engine readiness is two-stage: the SOCKS listener accepting TCP, then the HTTPS probe itself, which retries a bounded few times on transient curl exits (7, 28, 35, 56) because mihomo binds its listener before its tunnel reaches the running state and closes connections handed over in that window ("Send failure: Broken pipe"). Every attempt fails against a wrong credential, so the negative test still fails closed. It does not certify the production templates' individual rules beyond where unmatched traffic goes, Xray server compatibility, TUN integration, IPv6, QR decoding, browser/OS protocol registration, or platform-specific HWID behavior. The existing subscription-front tests cover HWID forwarding/cache isolation; physical client HWID behavior requires device evidence. Outline's existing provider tests remain the automated backend coverage; its application and transport are not exercised here.

## Running locally

Requirements: Docker Compose, Bun, Node 22/24, OpenSSL, and outbound access to the pinned GitHub releases and container registries. Linux x64 is the CI target; Docker Desktop with Rosetta emulation runs the amd64 engines and the Electron app on Apple Silicon. Runtime grows with the manifest's User-Agents because each native format runs its default route and all three endpoints. Node 22/24 is recommended for Playwright; the local Node 26 browser downloader has exhibited a hang.

For the report-form browser tests, install or update **Google Chrome stable** with its normal updater. The Chromium project uses that installed browser with `chromiumSandbox: true`, in a fresh automation profile. It never falls back to Playwright's downloaded Chromium or headless shell. The shared browser fixture checks the actual worker browser before loading a page: versions older than `156.0.8078.73` (the fix for CVE-2026-118306, CVE-2026-118331, CVE-2026-118348 and CVE-2026-118344), unrecognized versions, sandbox-disabling arguments and remote browser connections fail the run. Import `test` from `tests/compat/browser/fixtures.ts` in browser specs to retain this check. CI refreshes Chrome stable on every run; only Playwright's Firefox is downloaded and cached. A missing browser or unavailable sandbox is an error, never a reason to disable the sandbox.

SFL is a separate, pinned application under test with its own Electron runtime. Updating Playwright or Chrome does not update that runtime; the SFL import test does not claim that the packaged application's Chromium has received these CVE fixes. Its sandbox stays enabled in the container and desktop VM paths.

```sh
bun install --frozen-lockfile
bun run test:compat
bunx playwright install firefox
bun run test:compat:browser
bun --no-env-file scripts/compat/report.ts
```

The integration stack binds loopback port 3000 and the packaged-app bridge uses port 4179. Do not run it concurrently with another Remnawave integration stack. Both backend fixtures and generated private keys are throwaway. The wrapper always tears down its own Compose project and volumes; it never uses the application's production Compose project. `.cache/compat` and `test-results` are ignored by Git. The application runs with a fresh user-data directory.

Downloads verify pinned SHA-256 before extraction/execution. `FCP_COMPAT_CHANNEL=latest` instead resolves official stable release assets and their GitHub SHA-256 digests, then executes the same tests; this runs nightly separately from the pinned PR gate. It does not rewrite the committed pins. A changed upstream import UI or format fails discovery and requires review before updating the pins.

The public artifact contains test names, statuses, artifact versions/hashes and coverage limitations. Raw JUnit failures, generated configurations and engine logs are not uploaded because they can contain credentials. Browser traces/screenshots contain only fixture data. Packaged app screenshots are retained locally under `test-results/compat/sfl` for debugging.

## Edge connection

`bun run test:integration:edge-connection` (job **Member connects through an edge**) is the release gate for edges and the proof behind the supported matrix (`docs/edges.md` "Supported matrix", `tests/compat/manifest.ts` `edgeMatrix`): a member connects THROUGH an edge with real software end to end, for every cell the matrix claims. The subscription checks above prove what FCP serves; this one proves that what it serves after a node is protected actually carries a member's traffic through the intended edge, and around nothing else.

| Piece          | What runs                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Panel          | The ephemeral Remnawave panel of `docker-compose.remnawave-test.yml`.                                                                                                                                                                                                                                                                                                                                                                                              |
| Enrolled nodes | Real `remnawave/node`s the node role's contract enrolls, serving FCP's own profile: `freedom-reality` and `freedom-xhttp` (XHTTP under REALITY) on their public port, fronted at L4; `freedom-ws` on loopback behind its ingress (Caddy in the node's network namespace, TLS for the origin hostname), at L7.                                                                                                                                                      |
| Operator nodes | Real `remnawave/node`s serving a profile the operator wrote (`tests/edge-connection/cells.ts`), managed by the panel at their public address and served direct first: eight transports at L4 (VLESS over TLS, WebSocket, HTTP Upgrade, gRPC and XHTTP; Trojan over TLS and WebSocket; Shadowsocks), four HTTP transports at L7 (HTTP Upgrade, gRPC on 443, XHTTP packet-up, Trojan over WebSocket). Xray terminates TLS itself with a per-run certificate.         |
| L4 edge        | A plain TCP forwarder (`docker/edge-connection-test/forwarder.ts`) answering on one address per load balancer. The fake UpCloud API hands out the next address of its pool and wires it to exactly the backend FCP asked for.                                                                                                                                                                                                                                      |
| L7 edge        | A CDN-style front (Caddy): TLS for the fake Cloudflare zone, and one route per proxied record, added through its admin endpoint by the fake API: the record's content on the zone's port 443 or its Origin Rule's, the origin certificate verified, the front's hostname passed as the Host. As Cloudflare does, it sends the member's address in `X-Forwarded-For` always and in `CF-Connecting-IP` unless the record's request-header Transform Rule removes it. |
| Member         | The pinned sing-box and Mihomo of the compat suite, on a network that reaches only the edges.                                                                                                                                                                                                                                                                                                                                                                      |
| Page           | A web page on a network only the nodes join, answering a per-run token.                                                                                                                                                                                                                                                                                                                                                                                            |
| FCP            | `convex-test` in a runner container on the nodes' network, so its own checks (the ingress check, the origin probe, the front proof) reach the nodes the way production does.                                                                                                                                                                                                                                                                                       |

What the tests assert (`tests/edge-connection/`):

- **Wiring** (`wiring.integration.test.ts`, no FCP): with hand-written configs, a REALITY session through the forwarder and a WebSocket session through the front each fetch the page, and so does every operator transport through its own edge with every engine that speaks it; the member network reaches no node and no page directly, and the node's ingress sees the front, never the member. A failure here is the topology's, not FCP's.
- **Member** (`member.integration.test.ts`): for each enrolled node, enrollment and the role's applied report reach `machine_ready` (for the WebSocket node through FCP's own ingress check against the real ingress); a member issued into the node's mode gets nothing that names the origin while the node is not live; the guided setup run provisions through the real adapter, for L4 builds the real Try it link, which the engine that speaks it imports and connects through the candidate edge BEFORE the tick, for L7 runs the real front proof through the front and the node; the run parks at publish until the node is approved over the admin HTTP routes, then hides, rehearses over the panel's real bodies and goes live. For each operator node, the guided setup run discovers every transport, fronts each with its own edge (every L4 link tried before the tick, every L7 front proved, VLESS or Trojan), hides the direct Hosts and finishes without an approval (FCP does not manage the node). Then, per tested cell and per engine the cell claims, the member whose key lands on that cell's edge (a member gets a primary and a backup edge of the node's pool; the test re-keys until it is this one) fetches `/api/v1/sub/<token>` with the engine's User-Agent: every endpoint is one of the node's edges on 443, no node address or origin hostname appears, and the engine fetches the page through the cell's entry, counted by the forwarder at that edge's address or logged by the front for that hostname from the member's address. Through the WebSocket node's front, the node's ingress also logs what the front sent it: no `CF-Connecting-IP` (FCP's header rule for the front's name removed it) and the member's address in `X-Forwarded-For`, which no rule removes at Cloudflare and the node itself must drop (docs/edges.md "Cloudflare fronts"). Last, FCP reached nothing but the panel and the fake providers. Every tested cell of the manifest must have a case (`cells.ts` refuses a claim without one).

- **The WebSocket node's encrypted twin** (same file, after its cell; `docs/backends.md` "VLESS Encryption"): the encrypted transport is added on the real panel, made the mode's twin and switched on for the node; FCP's bootstrap answer must name the twin's route (the node's ingress in this stack carries exactly that route, as the node role deploys it); FCP's own encrypted session goes through the front to the twin's path; then the member's real Mihomo body must hold, for its front, the encrypted entry, the plain one behind it and the ordered group, and the pinned Mihomo fetches the page on the encrypted entry, on the plain one, and left to the group, which takes the encrypted one (read from the engine's own connection log: the group checks every member, so the node's ingress sees both paths; for that run the group's checks go to the stack's page, the network having no public internet). The sing-box body carries the plain entry alone and still connects.

Seams: the outside probe round that verifies an L4 standby (its evidence lands as Globalping's would), and two stand-ins inside the otherwise real L7 front proof (the front is dialled at its address instead of through public DNS; its neutral 204 is the stack's page). The provider APIs are fakes behind the real adapters. A served body is adapted to the sandbox before it runs, and only that (the test asserts the rendered proxies are untouched, `tests/edge-connection/clients.ts`): the TUN inbound is dropped (the container has no TUN device; a local listener carries the requests), the DNS servers point at the client network's resolver (it has no public one), a Mihomo body loses its controller and extra ports, and the test picks which of the body's proxies carries its request (sing-box `route.final`, a Mihomo `MATCH` rule). A Mihomo body keeps its own `mode` (in any other mode Mihomo ignores the picked rule), and before any of it the served body's own default route must take its proxies (`defaultRouteFaults`). An operator node's qualification and test-link credential is minted on the default mode's group, so the test makes that node's mode the default while its run goes (the operator's choice of mode for a node FCP does not manage).

Facts the stack pins down: Xray refuses sing-box and Mihomo over REALITY unless the transport sets `minClientVer` low enough (FCP's profile template sets `1.8.1`, which is what lets sing-box in; § "REALITY client versions"), and refuses to proxy to private or reserved addresses, RFC 5737 included, so the page's network uses a public-looking range that routes nowhere. A gRPC origin offers `h2` alone, so FCP's origin probe offers it too (an `http/1.1`-only handshake is refused and the transport would never be offered an L7 account). Mihomo's XHTTP needs HTTP/2 to the front: an XHTTP transport whose TLS offers only `http/1.1` reaches the front with nothing it will speak. The panel hands a node only the users that exist when it starts it, or that it adds once the node is up: a user created while a node is still starting can miss it, so the wiring test creates its user before its nodes (members of the lifecycle test are issued long after their node is up).

Locally it needs Docker (amd64 sing-box runs under emulation on Apple Silicon) and takes about two minutes once images and the runner's dependencies are cached (the first run pulls the images and installs dependencies into a Docker volume). It binds the panel's loopback port 3000 like the other Remnawave stacks, so never run it alongside them. The script always tears its project down; `EC_KEEP=1` leaves the stack up for debugging, and the next run starts with a teardown. Nothing it keeps outside `.cache/edge-connection-test` (wiped each run) and nothing it prints carries a credential: node logs, client configs and subscription bodies are never echoed, and CI uploads no artifact.

## REALITY client versions

Every REALITY client puts a version in its Client Hello, and the server lets it in only between the transport's `minClientVer` and `maxClientVer` (both inclusive). What each family sends:

| Client family                                                | Version it sends     |
| ------------------------------------------------------------ | -------------------- |
| Xray-based (v2rayN, v2rayNG, Happ)                           | its own Xray version |
| sing-box and the apps on it (SFA, SFI, SFM, Hiddify, Karing) | 1.8.1                |
| Mihomo and the apps on it (Clash Verge, FlClash)             | 1.8.2                |

A transport that sets no `minClientVer` has no minimum, except on Xray-core v26.7.11 to v26.7.28 (commit af7eb680), which take 26.3.27: there a hand-built transport admits recent Xray clients only, and every sing-box or Mihomo member fails with `reality verification failed` while a test made with an Xray client passes. `"minClientVer": "1.8.1"` admits every family on those releases. Commit 47cfe999 took the default out again (v26.9.8, a build later withdrawn as a release, and v26.9.9), and brought XTLS/REALITY 8cdf7bf9 with it: from then on the server refuses a Client Hello that does not offer X25519MLKEM768 ahead of X25519. sing-box strips that key share from its REALITY Client Hello (SagerNet/sing-box issue 4520, open as of sing-box 1.14.1), so no transport setting lets a sing-box client in on v26.9.8 or later. Mihomo sends it only when its configuration asks, which every body FCP serves does (below). FCP judges a transport it did not build before members move onto it (the protect plan, the test card, the adopt dialog) and keeps judging a protected one (attention `reality_refuses_clients`), each restriction named with its own fix; docs/edges.md § "Protecting a node FCP does not manage" has the details. After a node upgrade, test each family, not only an Xray client.

### The X25519MLKEM768 key share (Xray-core v26.9.8 and later)

A Client Hello the server refuses for want of the key share is handed to the target like a probe: the client sees the target's certificate and gives up (`REALITY authentication failed` in Mihomo, `reality verification failed` in sing-box), whatever `minClientVer` says. No server setting turns it off. A REALITY server understands X25519MLKEM768 since Xray v25.5.16, so a client that offers it connects to the releases before v26.9.8 too.

| Client                                                                                                    | Offers X25519MLKEM768                                                                                                                                                      | On Xray v26.9.8 or later                    |
| --------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------- |
| Xray-based, v25.5.16 or later, `chrome` fingerprint (FCP's Hosts carry it)                                | yes (by the REALITY author's account, `firefox` and `safari` too)                                                                                                          | connects                                    |
| Mihomo v1.19.9 or later with `reality-opts: {support-x25519mlkem768: true}` and the `chrome` fingerprint  | yes (its Chrome 133 print: GREASE, X25519MLKEM768, X25519)                                                                                                                 | connects: every body FCP serves asks for it |
| Mihomo without that key (every release through v1.19.33), Mihomo before v1.19.9, or another fingerprint   | no: Mihomo removes the key share unless asked (MetaCubeX/mihomo#2983, which would have kept it, was closed unmerged), and its Firefox, Safari, iOS and Edge prints lack it | refused                                     |
| Mihomo importing a share link                                                                             | only from a non-standard `support-x25519mlkem768` query parameter, which no backend writes                                                                                 | refused                                     |
| sing-box and the apps on it, every release (v1.14.4, v1.15.0-alpha.13 and branch `testing` on 2026-10-24) | no: `common/tls/reality_client.go` removes it whatever the configuration says                                                                                              | refused                                     |
| Stash                                                                                                     | not checked (closed source); its body asks like Mihomo's                                                                                                                   | unknown                                     |

What FCP does about it:

- **Mihomo.** Every Clash, Mihomo and Stash body FCP serves asks each REALITY entry for the key share, the XHTTP `download-settings` leg included (`support-x25519mlkem768: true`, `convex/lib/realityKeyShares.ts`), on every route and again when a cached body is served, unless the entry sets the key itself. The backend writes the key only for a Host whose Mihomo override is ticked (Remnawave `mihomoX25519`), which FCP never sets, so without this a Mihomo member on a v26.9.8 node is refused like a sing-box one. Older Mihomo ignores the key. The fingerprint stays the Host's: a hand-made Host on another fingerprint keeps Mihomo out of such a node, key or not.
- **sing-box.** No body can help it: the REALITY verdict marks every REALITY transport on such a node `core_key_share` (above). Until sing-box offers the key share, keep REALITY nodes that sing-box members use on Xray v26.7.28 or older, or give those members a mode without REALITY first. remnawave/node up to 3.4.3 bundles v26.7.28, and 3.4.4 (2026-11-02) bundles v26.10.31, so the test images are held at 3.4.3: Dependabot ignores 3.4.4 and later (`.github/dependabot.yml`), and the job **Node images' Xray vs the REALITY hold** (`scripts/compat/node-image-xray.sh`) fails any pinned node image whose own `xray version` is past v26.7.28. Read a new node image's Xray (`docker run --rm --entrypoint xray remnawave/node:<version> version`) before moving to it, the node role's pin included. The hold lifts once sing-box sends the key share.

The proof is `bun run test:integration:reality-keyshare` (job **REALITY key share vs Xray-core**, `convex/lib/realityKeyShares.integration.test.ts`): the pinned Mihomo and sing-box against a real Xray-core v26.7.28 (the node image's, the front check's pin) and v26.10.21, over REALITY on raw TCP with Vision and on XHTTP, each transport with `minClientVer` 1.8.1, a fresh key and client id per run. On v26.7.28 every client connects, with the backend's own Mihomo body and with FCP's. On v26.10.21 the backend's Mihomo body and sing-box are handed to the target (the test target's certificate is one no client trusts, so both engines log `x509: certificate signed by unknown authority`), and FCP's Mihomo body connects. The `download-settings` leg is checked offline only. It needs Docker and takes under a minute once the images and engines are cached; it never prints a configuration or an engine log, and `FCP_REALITY_KEEP=1` leaves the stack up for debugging. Both Xray pins move by hand (Dependabot ignores `xtls/xray-core`); the second stays past v26.9.8 on purpose.

## Post-quantum key exchange

Which app gets a post-quantum (PQ) key exchange in which connection mode, and the CI job that says so. PQ means something different per mode:

- **REALITY** (`privacy-reality`, `freedom-reality`, and `freedom-xhttp`, which is XHTTP under REALITY): the TLS 1.3 key exchange of the REALITY handshake, end to end between the app and the node. It is PQ when the server picks `X25519MLKEM768` (group `0x11ec`, the ML-KEM-768 + X25519 hybrid). The node's Xray-core picks it whenever the client offers it and falls back to X25519 otherwise, so the client decides.
- **WebSocket behind a CDN** (`freedom-ws`): the TLS ends at the CDN, so its key exchange is the CDN's business. The guarantee is the VLESS Encryption layer inside the stream (`mlkem768x25519plus`, `docs/backends.md` "VLESS Encryption"): the mode's encrypted twin, handed to a family by its `edge.render.clients.<family>.encryption` rule (`prefer` or `only` hands it out, `plain` does not).
- **Hysteria** (`privacy-hysteria`, off by default): the QUIC TLS key exchange. Not measured: the taps below forward TCP only, and reading a QUIC handshake means removing its Initial packet protection first (keys any observer derives from the connection id), which nothing here does yet.

The table is `tests/compat/pqMatrix.ts` with each family's compiled default rule; `convex/pqKeyExchange.test.ts` (in `bun run test`) fails when they drift apart, so print it again with `bun tests/compat/pqMatrix.ts` after changing either. A deployment can set a family's rule to `only` (the encrypted entry alone) or to `plain`; `only` changes nothing in the table, `plain` takes that family's `freedom-ws` cell to no.

How each kind of cell is proved, with the pinned engines (`yes` and pinned `no` are assertions; `not measured` means no CI job runs that app's engine):

- **REALITY, measured on the wire.** `docker/compat/tlsHello.ts` reads the Client Hello (the groups offered and the key shares sent) and the Server Hello (the group picked; a Hello Retry Request is not the pick) off a plain TCP stream, cleartext in TLS 1.3 and REALITY alike, keeping the group numbers only. Two harnesses carry it:
  - `bun run test:integration:reality-keyshare` (job **REALITY key share vs Xray-core**) puts a tap (`docker/compat/hello-tap.ts`) in front of the node image's core (v26.7.28) and v26.10.21. Through it, on REALITY raw TCP with Vision and on XHTTP: Mihomo with the Clash body FCP serves must end on `X25519MLKEM768`, and with the backend's own body (no `support-x25519mlkem768`) on X25519, which is why FCP adds the key; Xray-core v26.7.28 and v26.10.21 as clients, from the share link the backend writes (`fp=chrome`), must end on `X25519MLKEM768`; sing-box must offer no PQ group at all and end on X25519 (the pinned no: when a sing-box release offers it, this fails, and the hold on the node image's Xray (§ "REALITY client versions") can go).
  - `bun run test:integration:edge-connection` (job **Member connects through an edge**) reads the same handshake in its fake L4 edge (`docker/edge-connection-test/forwarder.ts`, `GET /hellos`), so the REALITY cells (`freedom-reality`, `freedom-xhttp`) are checked with the REAL bodies the panel and FCP serve: every connection Mihomo makes through the edge ends on `X25519MLKEM768`, every connection sing-box makes on X25519, and every REALITY entry of the share-link body the Xray apps get carries the `chrome` fingerprint (the one the Xray-core client above was proved with).
- **WebSocket, by the entry and the engine.** The reality-keyshare job also runs a VLESS Encryption inbound on the node image's core with a fresh `mlkem768x25519plus` key: Xray-core (both releases, from the link) and Mihomo (from its proxy) connect on the entry FCP renders for it, the same engines with a plain entry are refused (an encrypted inbound refuses every client that does not speak the layer, so connecting is the proof the layer ran), and sing-box refuses the configuration outright (its VLESS outbound has no `encryption`, the pinned no). The edge-connection job's encrypted-twin case connects Mihomo on the encrypted entry through the front, and then fetches each catalogued app's body for that front: the families handed the twin must get the `mlkem768x25519plus` entry first, the others no such entry at all.

Apps marked `not measured` run an engine CI does not (Hiddify's sing-box fork, Karing's own build, Shadowrocket, Anywhere, Throne). Their REALITY key exchange is their engine's; on `freedom-ws` the families they fall in decide what they are handed (Shadowrocket and Anywhere are read as `xray-links` and get the encrypted entry first, behind which the plain one stays with `prefer`). Hiddify gets the plain entry: its fork speaks VLESS Encryption only from app v5.5.5, and FCP cannot tell the versions apart by User-Agent. Mihomo before v1.19.13 ignores an `encryption` it does not know and is refused by an encrypted inbound, so a Mihomo app that old needs the plain fallback `prefer` keeps.

## Apps too old to connect

Every FreeSocks mode is VLESS. Apps on the original Clash core (Clash for Windows, ClashX, the original Clash for Android; User-Agents `clash`, `Clash/<ver>`, `ClashX/…`, `ClashforWindows/…`) have no VLESS, so the panel serves them its legacy CLASH template with no proxy, and the legacy core refuses to load it (an empty select group: "`use` or `proxies` missing"). FCP answers those apps the **app notice** instead (`docs/edges.md` § "Apps that get no connection"): a config of the same format whose only entries say the app is too old and which apps to install, and the member's account page says so for 7 days. A sing-box app at a node that serves only XHTTP gets the same kind of notice ("can't use this connection mode"). Old cores are not given another protocol: they are unmaintained since 2023.

How the notice bodies were checked:

- **Mihomo** (`mihomo -t`, the compat suite's pinned engine and v1.19.33 locally): the Clash notice loads, and run with a local listener every request fails at `127.0.0.1:1` (connection refused); the compat suite asserts the same on the body it is served.
- **sing-box** (`sing-box check`, v1.14.4 locally): the sing-box notice passes.
- **Legacy Clash core**: not run. Its v1.18.0 source (the Go module proxy's copy, matching `sum.golang.org`'s `h1:tic7ykTOCaT0mxwAkXo6QP3LN3Nps8oZz9atgr6TU8A=`) was read instead: `socks5` with `name`, `server` and `port` is a type it parses (`adapter/outbound/socks5.go`), `select` groups, `MATCH`, `mode: rule` and `log-level: warning` are all its own, and VLESS is no type of it (`adapter/parser.go`). No binary of it comes from a source that publishes checksums.

The apps the notice names come from the client catalog (`noticeApps`, `convex/lib/appNotice.ts`). A catalog name that reads as a legacy core is never named, so the default catalog's `Clash` entry (Clash Verge Rev) is left out of the notice and the notice reads "Install FlClash or Clash Party" (Clash Meta for Android sorts after Clash Party so that the two named cover desktops). Renaming that entry to `Clash Verge Rev` in **Client apps** lets the notice name it too.

## App User-Agents

FCP tells apps apart by the User-Agent of their subscription fetch (`convex/lib/edges/clientFamilies.ts`). The family decides the app's render rule, VLESS Encryption included (`edge.render.clients.<family>`), and an app FCP does not recognise lands in `other`, which is plain-only. `tests/compat/userAgents.ts` is the inventory: each app's default User-Agent as its own source (or, closed source, its developer) states it, the tag and commit it was read at, and the family and body FCP must give it. Anything not confirmed says so; most apps also let a member type their own User-Agent, which FCP cannot follow.

Three checks keep it honest:

- **`convex/clientUserAgents.test.ts`** (in `bun run test`, so CI): every string classifies to its family and format; the panel's default response rules (`convex/lib/backends/remnawaveUserAgent.ts`, a copy of Remnawave 3.4.11's), after FCP's rewrites, give it a body of that format and never the legacy Clash template; `other` only with a written reason; every enabled catalog app has an entry backed by its source or docs (Karing and Shadowrocket are the named exceptions), and the compat manifest fetches with at least one real string per catalog app, so the real-panel suite sees what the app sends.
- **Job "Latest upstream clients' User-Agents (discovery)"** (nightly, `scripts/compat/user-agent-drift.ts`): re-reads each recorded source line at the app's newest release (or its branch, for apps without tags) and fails when it is gone. Update the entry and let the test say whether FCP still agrees.
- **Rewrites for the panel.** The panel matches User-Agents with anchored regexes, so a few real ones get the wrong body. FCP asks for them under a form it recognises: FlClash's Windows (`clash/v…`, which the panel took for a legacy Clash core, so FCP answered the app notice) and Linux (`fl_clash/v…`) names become `FlClash/v…`; ClashX Meta's CFNetwork `ClashX%20Meta/…` gets its space back; Everywhere is asked for as its bundled Mihomo (it can only use a whole core config, never a link list). The official sing-box shells' rewrite is older (§ "What is proved").

**Plain until seen working (2026-11-22).** Shadowrocket, INCY, v2RayTun, FoXray and Loon read link lists but are not known to read VLESS Encryption from a link (FoXray's last known core predates it, Loon's manual lists none, and Shadowrocket's reports conflict), so they take the plain rule of `other`. With them out of `xray-links`, that family can be encrypted-only without leaving any of them an entry they cannot speak.

## Full desktop VMs

The Debian container smoke test is not a desktop test. The **Client compatibility (desktop VMs)** workflow (`.github/workflows/client-compat-desktop.yml`) runs the same SFL adapter in a real desktop session: `scripts/compat/desktop-vm.sh` boots a pinned distribution image (its SHA-512 checked) under KVM on a standard hosted runner, with QEMU from a digest-pinned image, and cloud-init provisions Xfce under LightDM on Xorg with automatic login. The verified `.deb` is installed with apt, so the package's own postinst starts the real `sing-box-daemon` service, as on a member's machine. The panel, the engines and the harness stay on the runner; `FCP_COMPAT_SFL_REMOTE=scripts/compat/sfl-remote.sh` runs the driver inside the VM's Xfce session over SSH, with the session's own `DISPLAY`, `XAUTHORITY` and `DBUS_SESSION_BUS_ADDRESS` read from its `xfce4-session` process (a run without an Xfce session fails), and the subscription port forwarded to the VM's loopback. The app's result and screenshot are uploaded (fixture data only).

| Target           | Image                                                       | Typical run                               |
| ---------------- | ----------------------------------------------------------- | ----------------------------------------- |
| `debian-13-xfce` | Debian 13 `generic` cloud image, build pinned in the script | about 5 minutes (2 to boot and provision) |

Standard hosted runners for this public repository expose `/dev/kvm` (the job's udev rule opens it to the runner user) and cost nothing, so the matrix needs no larger runner and no self-hosted machine. The VM goes away with the runner, so pull-request code may run here: the workflow runs on pull requests that change the desktop path, on pushes to main, nightly and by hand. For reference if that changes: a 4-core larger runner costs $0.012 a minute, about $0.06 a run; a self-hosted desktop VM must be reset after every job and must never run pull-request code.

MX Linux 25.2 (the other distribution the matrix named) publishes no cloud image, only a live ISO, so it is not in the matrix yet: booting it means extracting the ISO's kernel and initrd, adding a serial console and an SSH key to the live system, and pinning the ISO's checksum. A target is added to `image_for` in `scripts/compat/desktop-vm.sh` and to the workflow matrix.

The nightly schedule also runs the provider contract test against a Remnawave 2.x backend (`REMNAWAVE_TEST_IMAGE=remnawave/backend:2.8.0`): production runs 3.x, but the provider stays dual-contract for backends that have not upgraded, and nothing on the PR gate boots a 2.x backend.

`FCP_COMPAT_SFL_EXECUTABLE` still drives an app installed on the machine that runs the suite, for a desktop where the harness itself runs inside the session.

## Deployed canaries

The smoke reads a dedicated canary subscription: a test account, never a member's, on a tier with no traffic or device limit (so the idle-free sweep never reclaims it). `scripts/compat/make-canary.sh` makes one on a stack host, from the stack checkout, through the deployer container: it creates the account as a sign-up does, grants it the `member` tier for ten years and issues its key into the default mode. It prints no secret: the account number and the targets file go to root-only files in `/root/fcp-canary`. Never sign in with the canary's account number or regenerate its key; that rotates the URL and the smoke fails. Device tests use a separate account (`docs/client-device-checklists.md`).

```sh
bash scripts/compat/make-canary.sh .env.beta https://<the site's public origin>
```

The `client-compatibility` Actions environment holds the targets as the secret `FCP_COMPAT_SMOKE_TARGETS`. Create the environment limited to the main branch, then pipe the file in without displaying it:

```sh
gh api -X PUT repos/<owner>/<repo>/environments/client-compatibility --input - <<'EOF'
{"deployment_branch_policy": {"protected_branches": false, "custom_branch_policies": true}}
EOF
gh api -X POST repos/<owner>/<repo>/environments/client-compatibility/deployment-branch-policies -f name=main -f type=branch
ssh root@<stack host> cat /root/fcp-canary/smoke-targets.json | gh secret set FCP_COMPAT_SMOKE_TARGETS --env client-compatibility --repo <owner>/<repo>
```

The file holds one target named after the stack. For a mirror, add an entry by hand:

```json
[
  { "name": "primary", "url": "https://example.test/api/v1/sub/DEDICATED_CANARY" },
  { "name": "mirror", "url": "https://mirror.example.test/api/v1/sub/DEDICATED_CANARY" }
]
```

Run **Deployed client compatibility** after deploying or changing a CDN/mirror configuration. Missing targets fail explicitly. HTTP redirects, errors, empty/wrong formats, unsafe shared-cache responses and invalid native configs fail. Once per target, the `revalidate` stage fetches the canary as identity, gzip and zstd: each answer must carry the same weak `W/"fs1-…"` validator (a proxy that rewrites or suffixes it fails), a compressed answer must vary on `Accept-Encoding`, and sending the validator back must return 304 (once per target because the per-token throttle would not carry it for every client). This workflow never creates, rotates or deletes an account. Device-limit testing is a separate capability check.

## Application certification and adding coverage

`tests/compat/manifest.ts` records each catalog client's scope and remaining gaps. Add an entry whenever adding a default recommendation. For CMS-only recommendations, review/export the live catalog before a release: the offline coverage guard cannot inspect a production database. Add an adapter for the actual package instead of relabeling a shared engine test as application coverage.

Apps needing Apple hardware, Android devices, licensed installs or missing automation are explicitly unverified. `scripts/compat/certify.ts` fails until every recommended app has recent application evidence for the exact requested FCP commit in `tests/compat/application-evidence.json`. The committed file starts empty intentionally. Set `FCP_COMPAT_CERTIFY_COMMIT` and run the command as a release checklist gate; never invent passes to make it green. `docs/client-device-checklists.md` is the per-app device checklist, and `scripts/compat/evidence.ts` writes a record only after the tester confirms every check. Each entry records:

- client, exact app version, OS, backend version and 40-character FCP commit;
- UTC `testedAt`, tester, and a URL to the test evidence;
- `import`, `connection`, `dns`, `https`: `passed`;
- `refresh`: `passed` (or `not-applicable` for Outline's static key);
- for a record made with `--hysteria2`, a `hysteria2` block (`rawImport`, `udp`, `wrongPinRefused`: `passed`), the checks in `docs/client-device-checklists.md` § "Hysteria". Only such a record lets the catalog mark the app `hysteria2: true` (§ "Hysteria in the client catalog").

Evidence expires after 30 days and certifies only the recorded configuration/version/OS. This is the place to attach full TUN/device tests; the automatic engine and SFL import jobs alone cannot certify every client. Configure branch protection to require **Subscriptions, engines and packaged SFL** and **Report form (Chromium and Firefox)**. ## XHTTP in the client catalog

Each catalog app carries an `xhttp` flag (`convex/lib/clientCatalog.ts`), tri-state like `ipv6`: `true` means the app connects on an XHTTP-under-REALITY entry (the `freedom-xhttp` mode), `false` means it can't, and unset means untested. The value is what reaches the app through FCP's delivery, not what its own core could do. Karing's core has XHTTP, but FCP serves it sing-box bodies and the panel builds those without XHTTP, so Karing is `false`. `convex/clientCompatibility.test.ts` holds that rule: a default app whose manifest format is `singbox` or `outline` can't be `true`.

The defaults come from release notes and source, checked 2026-11-02. None is device-tested.

| `xhttp` | Apps                                                                                                                                                                                                             |
| ------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `false` | sing-box, Karing, Outline                                                                                                                                                                                        |
| `true`  | Hiddify (v4.0.4 or later), v2rayNG, v2rayN, Throne, Anywhere, Clash (Clash Verge Rev 2.5.0 or later), FlClash (0.8.93 or later), Clash Meta for Android (2.11.37), Clash Party (1.9.5 or later, as Mihomo Party) |
| unset   | Shadowrocket (XHTTP under REALITY unverified)                                                                                                                                                                    |

The member setup page (`ConnectClient.svelte`, on `/account` and `/get-account`) reads it. When the member's effective connection mode is an XHTTP mode, apps marked `false` are left out and one line says why (`setup.xhttpOnly`). Untested apps stay, and other modes show every app. `isXhttpMode` in `src/shared/xhttpModes.ts` decides which modes count (the app notice reads it too): today only the built-in `freedom-xhttp`, so an admin-created XHTTP mode needs its slug added there. The flag only changes which apps the page offers. It never changes a subscription body.

### Getting the defaults onto a running deployment

A deployment whose `clients` table is empty reads `DEFAULT_CLIENTS` directly and has the flags at once. A seeded one doesn't. Each deploy's `seedCutover` runs `seed:seedClients`, which only inserts missing apps, so existing rows stay untested and every app stays visible until one of these is done:

- Run `seed:refreshDefaultClients` once through the deployer container (`docs/beta-deploy.md` § "One-off functions"). It rewrites every default-managed field on the default apps (install URL, platforms, backends, import scheme, HWID, open-source metadata, ease of use, `ipv6`, `xhttp` and priority). It keeps each row's `enabled` flag, any admin description and admin-added apps. Look over **Client apps** in the admin first: the refresh undoes hand edits to those fields on default apps.
- Or set **XHTTP support** per app in **Client apps** → Edit. Nothing else changes.

Do one of them before turning the `freedom-xhttp` mode on for members.

## Hysteria in the client catalog

Each catalog app also carries a `hysteria2` flag (`convex/lib/clientCatalog.ts`), tri-state again, but read as an **allowlist**: on a Hysteria mode (the built-in `privacy-hysteria`) only apps marked `true` are offered, and untested ones are left out with the ones marked `false`. The entry's certificate is self-signed and trusted only by its pin (`docs/privacy.md`), and the Hysteria password is the member's own credential. An app that drops the pin either fails to connect or connects to whoever answers at the address and hands that server the password. So `true` is never set from release notes or from what an app's core can do: it needs a recorded check of that app's version through FCP's own delivery.

| `hysteria2` | Apps                                                                                                                      |
| ----------- | ------------------------------------------------------------------------------------------------------------------------- |
| `false`     | Hiddify (its link parser ignores `pinSHA256`, so the pin never reaches its core)                                          |
| unset       | Every other app, until a record exists. Likely first: v2rayNG and v2rayN (Xray-core reads `pinSHA256` from the link list) |

What counts as a record: an entry in `tests/compat/application-evidence.json` made with `scripts/compat/evidence.ts --hysteria2`, for a specific app version, after the three Hysteria checks in `docs/client-device-checklists.md` § "Hysteria": the app imports a `privacy-hysteria` key's raw config through its own importer, connects through the `· UDP` entry over UDP, and refuses to connect once one character of the entry's pin is changed. `convex/clientCompatibility.test.ts` fails when a default app is `true` without such a record for it. An admin who sets **Hysteria support** in **Client apps** is held to the same rule by the field's own help text; the CMS cannot see the evidence file.

Three places read it, through `appFitsMode` in `src/shared/hysteriaModes.ts` (`isHysteriaMode` decides which modes count: an admin-created Hysteria mode needs its slug added there):

- **The setup page** (`ConnectClient.svelte`) offers only `true` apps and says so in one line (`setup.hysteriaOnly`). A platform with none says to pick another connection mode (`setup.hysteriaNoApps`), never the usual "use any compatible client".
- **The app notice** (`convex/lib/appNotice.ts`) names only `true` apps for a member on a Hysteria mode, and none when there are none.
- **Availability** (`resolveCatalogWithAvailability`, `convex/lib/placement.ts`): a Hysteria mode is available on a backend only while an enabled app on that backend is `true`, besides the backup and serving rules. The CMS refuses to turn the mode on, or to give it a backend, where no such app exists, and says why. Disabling the last such app later takes the mode out of the catalog rather than leaving members with nothing to install.

To turn `privacy-hysteria` on: record an app, set its default to `true` in `DEFAULT_CLIENTS` with the record in the same pull request (or set **Hysteria support** in **Client apps** after the same check), run `seed:refreshDefaultClients` on a seeded deployment, then enable the mode. The engines behind the record are proved in CI by the Hysteria job (§ "Hysteria engines").

### Hysteria engines

`bun run test:integration:hysteria` (`scripts/compat/hysteria.sh`, the **Hysteria vs Xray-core** job) proves the pieces a device record cannot: a real Xray-core of the release the node image runs serves FCP's own Hysteria inbound (`convex/lib/backend/profileTemplate.ts`, with its self-signed certificate), and the pinned engines connect through it from the entry FCP's delivery would hand them:

- Xray-core from a `hysteria2://` link (the link list the Privacy raw config carries), sing-box from its outbound, Mihomo from its proxy, each with the pin in its own form (`pinSHA256` hex, `certificate_public_key_sha256` base64 SPKI, `fingerprint` hex);
- a UDP datagram round trip through each engine to an echo service behind the server, so the tunnel carries UDP, not only TCP;
- a rogue Xray-core answering in the node's place (the entry's server pointed at it, as a hijacked route would) with another certificate for the same name, which accepts the member's password: each engine refuses it (sing-box: `unrecognized remote public key`, Mihomo: `certificate fingerprints do not match`) and the rogue's access log carries **nothing** for the member, so no engine handed it the password (had one, the rogue would have accepted it and carried the request). A control run with the rogue's own pins then gets through and is logged, so the refusal is the pin, not a broken rogue.

It needs Docker and takes under two minutes once the images and engines are cached; it never prints a configuration or a log, and `FCP_HYSTERIA_KEEP=1` leaves the stack up for debugging. The Xray pin moves by hand with the other Xray-core pins of `docker-compose.compat.yml`.

### Hysteria on the backend

Two more runs prove the backend side, with FCP's own transport, certificate and Host:

- **Every app's body passes the guard.** `convex/lib/backends/remnawave.hysteria.integration.test.ts`, in `bun run test:integration:remnawave` (CI): the test backend takes FCP's Hysteria transport beside a REALITY one and FCP's Hysteria Host as FCP writes it (`desiredExtraHost`: the pin, h3, TLS and the per-format rewrites), and reads the pin and the rewrites back. A key placed in both groups then gets a body for every User-Agent of the client manifest, and each one that carries Hysteria passes `guardHysteria` with nothing dropped, every entry verified by the expected pin. With the rewrites in place the guard never has anything to drop.
- **A real node serves it.** `convex/lib/backends/remnawave.hysteria.node-integration.test.ts`, in `bun run test:integration:remnawave-node` (manual, Docker; one file: `bun run test:integration:remnawave-node convex/lib/backends/remnawave.hysteria.node-integration.test.ts`): `remnawave/node` 3.4.3 applies the profile and serves Hysteria on UDP 443 beside REALITY on TCP 443 to one key in both groups; a key added while it runs is served without an Xray restart; the backend counts Hysteria bytes to the key; a disabled key is refused on both on a new connection; and after a regenerate (FCP deletes the key and issues a new one) the old password is refused while the new one is served.

**Open connections outlive a disable.** Hysteria authenticates once per QUIC connection, and an app keeps one connection open and sends every request over it. On the node release the fleet runs (Xray v26.7.28 in `remnawave/node` 3.4.3), a connection opened before the key was disabled went on carrying its requests for the whole five minutes the test watched (2026-11-06). Only a new connection is refused. REALITY authenticates every TCP connection, so there a disable takes effect on the app's next connection. The node test records how long it took (`observed.openHysteriaCutAfterDisableMs`, null when it was not cut within `RW_TEST_OPEN_WATCH_MS`). Until something cuts open connections, disabling a key (a lapsed membership, an abuse ban, a device limit) does not stop a Hysteria app that stays connected.
